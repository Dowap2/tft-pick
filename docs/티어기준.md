# 덱 티어 산정 기준 (v4 · 2026-09-21)

이 문서가 **단일 기준**이다. 코드(SQL 함수·수집기·설명 페이지)가 이 문서와 다르면 **코드가 틀린 것**이다.
기준을 바꾸려면 이 문서를 먼저 고치고, 아래 "반영 위치"의 파일을 맞춘다.

---

## 1. 수집 범위

| 항목 | 값 |
|---|---|
| 지역 | KR (`kr.api.riotgames.com` / `asia.api.riotgames.com`) |
| 큐 | 랭크만 (`queue_id = 1100`) |
| 세트/패치 | `patches.is_current = true` 인 세트만. 다른 세트 매치는 버림 |
| 시드 티어 | 챌린저 · 그랜드마스터 · 마스터 · **다이아몬드 · 에메랄드** |
| 수집 주기 | **2분마다 1사이클**, 하루 종일 (GitHub Actions 3시간 잡 × 8회/일, `23 */3 * * *` UTC) |
| 사이클당 | 시드 12명의 최근 매치 목록 + 신규 매치 최대 60판 (= 요청 약 72회 / 한도 100) |
| 레이트 리밋 | 20 req/s, 100 req/2min — 수집기 내부 리미터가 두 창을 동시에 만족. 429 는 `Retry-After` 만큼 대기 |

하루 예상 적재량 ≈ 매치 43,000판 / 보드 344,000개. (현재 값은 모두 CLI 플래그로 조절 가능 — §7)

## 2. 랭크 그룹

매치 하나에 그룹 하나를 붙인다. 그 매치를 찾아준 시드 플레이어의 티어로 정한다
(TFT 랭크 게임은 같은 구간끼리 매칭되므로 시드 티어 ≈ 매치 전체 수준).

| 그룹 | 티어 |
|---|---|
| `apex` | 챌린저 · 그랜드마스터 · 마스터 |
| `high` | 다이아몬드 · 에메랄드 |

한 매치를 여러 그룹의 시드가 동시에 물고 오면 `apex` 가 이긴다.

**티어 산정에는 두 그룹을 섞는다.** 이 사이트가 답하려는 건 "챌린저에서만 되는 덱"이 아니라
**챌린저부터 에메랄드까지 공통으로 먹히는 덱**이다. 구간을 나눠 상위만 보면 그 답이 안 나온다.

그룹 구분은 버리지 않고 `deck_stats.games_apex / avg_place_apex / games_high / avg_place_high` 로 남긴다 (티어 계산에는 안 씀).
"챌에선 1등인데 에메에선 5등"인 덱을 나중에 가려내려면 이 값이 필요하다.

표본 비율은 시드 수가 정한다 — 현재 apex 약 3,000명 : high 약 400명이라 수집되는 매치도 **apex 가 다수**다.
섞는다고 에메랄드 기준이 되는 게 아니다. 비율을 바꾸려면 `--per-tier` 를 조절한다.

## 3. 데이터 보존과 통계 표본

**통계 표본은 보드 보존 기간과 무관하다.** 이게 v4 의 핵심 변경이다.

v3 까지는 `cluster-decks` 가 매번 전부 지우고 남아있는 보드로 다시 만들었다.
그래서 "통계 표본 = 보드 보존 기간" 이었는데, 보드는 용량의 95% 를 먹는다.
표본을 키우면 용량이 터지고 용량을 아끼면 표본이 말랐다 (실측: 보드 7,184 → 444개, 덱 53 → 7개).

이제 클러스터링할 때마다 **덱별·시간별 집계**를 `deck_stat_buckets` 에 누적한다.

| 저장물 | 보존 | 크기 | 쓰임 |
|---|---|---|---|
| 보드 상세 (`units`/`traits` jsonb) | **6시간** | 1.6KB/보드 | 클러스터링(3시간 주기)이 두 번 볼 수 있으면 충분 |
| 매치·참가자 행 (등수·레벨) | **24시간** | 0.14KB/행 | 버킷에 집계되고 나면 쓸모없다 |
| **통계 버킷** | **8일** | **0.06KB/행** | 덱별 `(시각, 판수, 등수합, 1등수, top4수)` |

버킷은 53덱 × 24시간 × 7일 ≈ 9천 행. **보드 한 시간치보다 작다.**
`deck_stats` 는 이제 머티리얼라이즈드 뷰가 아니라 버킷 위의 일반 뷰라, 리프레시가 필요 없고 항상 최신이다.

**겹쳐 계산해도 안전한 규칙**: 수집 창이 겹쳐 돌기 때문에 같은 시간대가 여러 번 집계된다.
버킷은 **판수가 늘었을 때만 덮어쓴다**. 부분 집계가 꽉 찬 집계를 덮어써서 표본이 줄어드는 걸 막는다.

**약점**: 덱 id 가 바뀌면 누적이 끊긴다(그 덱은 표본이 0부터 다시 쌓인다).
사라진 덱의 버킷은 8일간 남지만, 티어 계산은 **살아있는 덱만** 대상으로 하므로 S 자리를 차지하지 않는다.

## 4. 덱을 정하는 기준 (클러스터링)

1. 보드 = 유닛 집합. 유닛 5개 미만 보드는 버림.
2. 최종 보드(8레벨 이상)끼리 **자카드 유사도 ≥ 0.5** 면 같은 덱. 2패스로 안정화, 대표끼리 0.7 이상 겹치면 병합.
3. 대표 유닛 = 그 묶음에서 **등장률 50% 이상**인 유닛.
4. 표본 **15판 미만** 묶음은 버림.
5. 중반 탈락 보드(최종 레벨 ≤ 7)는 새 덱을 만들지 않는다. 대표 유닛 + metatft 유사 덱의 4~7렙 라인에 **70% 이상 포함**되면 그 덱의 중간 단계 표본으로 붙는다.
6. 덱 최종 조합 = 등장률 30% 이상 유닛, 코어 = 캐리 + 등장률 상위 2명.
7. **캐리 = 아이템을 가장 많이 받는 유닛**(인스턴스당 평균 개수, 동률이면 고코스트). 이름 = 최다 활성 시너지 + 캐리 이름.
   - 공격템만 세지 **않는다.** 가고일·워모그를 끼고 캐리하는 유닛(말파이트 등)을 영영 놓치기 때문이다.
     실측: `치명적인 꽃` 덱에서 말파이트가 2.39개로 아이템을 몰아받는데, 전부 방어템이라 1.47개짜리 소라카가 캐리로 뽑혔다.
   - 부작용은 감수한다 — 진짜 탱커가 캐리로 표기되는 덱이 생길 수 있다. 그 편이 캐리를 통째로 놓치는 것보다 낫다.

## 5. 어떤 덱이 티어 리스트에 들어가나

§4 로 만들어진 덱 중, **아래 네 가지를 전부** 통과한 것만 화면에 나오고 티어가 붙는다.

| # | 조건 | 값 | 탈락하면 |
|---|---|---|---|
| 1 | 현재 패치 | `patch_id = patches.is_current` | 지난 패치 덱은 안 보임 |
| 2 | 게시 상태 | `decks.is_published = true` | 수동으로 내린 덱 |
| 3 | 표본 | **`games ≥ 30`** (챌린저~에메랄드 합산) | "표본 부족"으로 제외 |
| 4 | 성적 | **`avg_place < 4.75`** | "평균 이하 덱"으로 제외 |

4번이 사실상의 하한선이다. 8인 게임의 기대 평균은 4.5등이므로 **4.75등을 넘는 덱은 아예 티어를 받지 못하고 목록에서 사라진다.**
즉 C 티어는 "나쁜 덱"이 아니라 **"자격은 통과했지만 그중 하위권"** 이라는 뜻이다. 진짜 나쁜 덱은 애초에 안 보인다.

그 앞 단계에서 이미 걸러진 것들 (§4):
- 유닛 5개 미만인 보드 → 클러스터링 대상 아님
- 표본 15판 미만인 묶음 → 덱으로 승격 안 됨 (30판 자격과 별개로, 이 단계에서 먼저 죽는다)
- 최종 레벨 ≤ 7 인 중반 탈락 보드 → 새 덱을 못 만들고 기존 덱의 중간 단계 표본으로만 붙음

## 6. 티어 컷 (OP · S · A · B · C)

### 6.1 쓰는 값은 두 개뿐

| 이름 | 정의 |
|---|---|
| `avg_place` | 그 덱을 쓴 보드의 평균 등수 (1~8, **낮을수록 좋음**) |
| `win_rate` | 1등 비율 (**높을수록 좋음**) |

TOP4율·픽률은 **티어 계산에 쓰지 않는다** (화면에는 보여준다). 1등과 평균 등수, 두 축이면 충분하고 나머지는 이 둘과 거의 같이 움직인다.

### 6.2 순위로 바꾼다 — 절대 점수가 아니라 상대 순위

두 값을 각각 `percent_rank` 로 0~1 사이 순위로 환산한다. **0.0 이 1등, 1.0 이 꼴찌.**

```
win_pct   = percent_rank() over (order by win_rate  desc)   -- 승률 순위
place_pct = percent_rank() over (order by avg_place asc)    -- 평균 등수 순위
```

- 공식은 `(내 등수 - 1) / (전체 덱 수 - 1)`. 자격 덱이 21개면 1등 = 0.00, 7등 = 0.30, 꼴찌 = 1.00.
- 동점은 같은 순위를 받는다 (승률이 똑같은 덱 둘은 둘 다 같은 `win_pct`).
- 자격 덱이 1개뿐이면 `percent_rank` 는 0 이다 → 그 덱이 OP 가 된다. 표본 초기에는 이럴 수 있다.

### 6.3 자르는 순서

**위에서부터 순서대로** 적용하고, 한 번 티어를 받은 덱은 아래 단계에서 빠진다.

| 순서 | 티어 | 조건 | 개수 |
|---|---|---|---|
| 1 | **OP** | `win_pct ≤ 0.10` **AND** `place_pct ≤ 0.10` **AND** `games ≥ 100` | 0~몇 개 (없을 수 있음) |
| 2 | **S** | 남은 덱을 `win_pct + place_pct` 오름차순 정렬 → **상위 5개** | 최대 5개 (남은 게 5개 미만이면 전부) |
| 3 | **A** | 남은 덱의 `percent_rank` ≤ **0.30** | 약 30% |
| 4 | **B** | 남은 덱의 `percent_rank` ≤ **0.70** | 약 40% |
| 5 | **C** | 나머지 | 약 30% |

- **OP 는 유일하게 "둘 다 상위 10%"를 요구하는 자리다.** 승률만 1등이고 평균 등수가 중간인 덱(1등 아니면 8등 하는 도박 덱)은 OP 가 못 된다. 이게 OP 의 정의다 — *안정적으로 잘 하면서 1등도 많이 하는 덱*.
- **OP 는 표본 하한이 따로 100판이다.** 자격 하한(30판)을 겨우 넘긴 덱이 평균 2.8등을 찍고 227판짜리 검증된 덱 위에 서는 일을 막는다. 100판 미만인데 성적이 좋은 덱은 **탈락이 아니라 S 후보로 내려간다** — 판수가 쌓이면 자동으로 OP 로 올라온다. OP 가 0개인 날이 정상이다.
- S 는 **개수 고정(5개)** 이라 비율이 아니다. 자격 덱이 27개면 S 는 전체의 19%, 60개면 8% 가 된다. 표본이 커지면 이 5를 손볼 것.
- A/B/C 의 30/40/30 은 `percent_rank` 기준이라 **정확히 30%가 아니라 근사치**다 (21개면 7/8/6 개로 갈린다).

### 6.4 이게 상대 기준이라는 뜻

**"평균 4.1등부터 S" 같은 고정 숫자는 없다.** 같은 3.9등 덱이 오늘은 S, 내일은 A 일 수 있다 — 주변 덱이 더 좋아지면 밀린다.

| 장점 | 단점 |
|---|---|
| 항상 OP·S 가 채워져서 "그래서 뭘 하라고?"에 답이 된다 | 메타 전체가 나빠도 누군가는 OP 가 된다 |
| 메타가 바뀌면 컷이 자동으로 따라온다 | 어제의 S 와 오늘의 S 가 같은 실력을 뜻하지 않는다 |
| 패치마다 숫자를 다시 튜닝할 필요가 없다 | "몇 등부터 S냐"는 질문에 그날의 데이터를 봐야 답할 수 있다 |

이건 **의도한 선택**이다. 절대 수치 컷(예: `평균 ≤ 4.10 이면 S`)으로 가려면 이 문서를 v4 로 올리고 `calculate_deck_tiers` 를 같이 고쳐야 한다.

### 6.5 오늘의 컷이 몇 등인지 확인하는 법

상대 기준이라 "지금 S 커트라인"은 쿼리로 본다. Supabase SQL Editor 에서:

```sql
select t.tier_label,
       count(*)                       as 덱수,
       min(s.avg_place)               as 최고_평균등수,
       max(s.avg_place)               as 최저_평균등수,
       round(avg(s.win_rate)::numeric, 4) as 평균_승률
from calculate_deck_tiers((select id from patches where is_current)) t
join deck_stats s on s.deck_id = t.deck_id
group by t.tier_label
order by min(s.avg_place);
```

`최저_평균등수` 가 그 티어의 커트라인이다. 이 값이 며칠째 4.6등 근처에서 놀면 자격 기준(4.75)을 조일 때다.

### 6.6 알려진 함정

- `ntile(100)` 으로 비율을 자르면 **안 된다.** 행이 100개보다 적으면 각 행이 버킷 1,2,3… 을 하나씩 받아, 21개짜리 목록은 전원 `bucket ≤ 30` = 전원 A 가 된다. (v3 까지 실제로 이 상태였다 — B·C 가 한 번도 안 나왔다. `0011_tier_percentile_fix.sql` 에서 `percent_rank` 로 교체.)
- 자격 덱이 6개 이하면 OP 몇 개 + 나머지 전부 S 가 되어 A/B/C 가 비는 게 정상이다. 표본 초기의 정상 동작이지 버그가 아니다.
- `deck_stats` 는 머티리얼라이즈드 뷰다. **리프레시 전에는 티어가 안 바뀐다** (매시 20분, 클러스터링 직후).

## 7. 조절 가능한 값 (기본값)

| 값 | 기본 | 위치 |
|---|---|---|
| 수집 주기 | 120초 | `--loop 120` |
| 사이클당 신규 매치 | 60판 | `--max-matches 60` |
| 사이클당 시드 수 | 12명 | `--seeds-per-cycle 12` |
| 시드 목록 갱신 | 60분 | `--reseed-min 60` |
| 다이아/에메 티어당 시드 상한 | 300명 | `--per-tier 300` |
| 잡 1회 지속 | 170분 | `--duration-min 170` |
| 덱 자격 표본 | 30판 | §5, `calculate_deck_tiers` |
| **OP 표본 하한** | **100판** | §6.3, `calculate_deck_tiers` |
| 덱 최소 표본 | 15판 | `cluster-decks.mjs --min-members 15` |
| 클러스터 유사도 | 0.5 | `cluster-decks.mjs --sim 0.5` |
| 클러스터 보드 상한 | 120,000 | `cluster-decks.mjs --max-boards 120000` |
| **보드 보존** | **6시간** | §3, `0014_stat_buckets.sql` |
| 매치 행 보존 | 24시간 | §3, `0014_stat_buckets.sql` |
| 통계 버킷 보존 | 8일 | §3, `0014_stat_buckets.sql` |
| 통계 집계 창 | 7일 | §5, `deck_stats` 뷰 |

병목은 Riot API 가 아니라 Supabase 용량(무료 500MB)이다. 측정값: 보드 1개 1.6KB, 매치 1판 = 보드 8개 = 12.8KB.
현재 설정(60판/사이클 = 43,000판/일)에서 보드 6시간 보존이면 상시 약 140MB. API 예산은 72/100 으로 아직 여유가 있다.
더 올리려면 **보드 보존 시간**을 먼저 보라 — 통계 표본은 버킷에 있으므로 보드를 줄여도 표본은 줄지 않는다.

| cdragon/metatft 스냅샷 · 이미지 | 매일 KST 06:00 |

## 9. 한계 (지켜야 할 정직함)

- Riot API 에 라운드별 보드가 없다. 4~7레벨 조합은 자체 표본 5판 미만이면 metatft 초반 통계를 빌린다. `borrowed` 로 표시.
- 배치도 위치는 실측이 아니라 특성 기반 자동 배치.
- 증강은 현재 세트 API 응답에 티어가 없어 metatft 큐레이션을 쓴다.
- 티어는 구간 평균이다. 챌린저와 에메랄드에서 성적이 갈리는 덱도 하나의 티어로 뭉뚱그려진다. `games_apex / games_high` 로 확인할 수 있지만 아직 화면에는 안 보여준다.
